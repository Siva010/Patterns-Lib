Find Minimum in Rotated Sorted Array II / visualized

Same loop as LeetCode 153, same three lines, one extra branch — and that branch is why this problem is Hard. In 153 the values are distinct, so nums[mid] versus nums[hi] always identifies which side is sorted. Drop distinctness and the case nums[mid] == nums[hi] becomes possible, and it tells you nothing at all: the minimum may lie on either side of mid. The only move that is provably safe is hi-- — discard exactly one element, not half the array. That one line costs you the O(log n) guarantee.

The branch that makes this Hard: nums[mid] == nums[hi]

Two arrays that are indistinguishable from mid and hi alone:

  • [1, 1, 1, 0, 1] — mid = 2, nums[mid] = 1 == nums[hi] = 1. The minimum 0 is right of mid.
  • [1, 0, 1, 1, 1] — mid = 2, nums[mid] = 1 == nums[hi] = 1. The minimum 0 is left of mid.

Identical probe, identical comparison, opposite answers. So no rule of the form “on ==, go left” or “on ==, go right” can be correct — either choice throws away the minimum on one of these two inputs. That is the whole difficulty of 154 in one line.

Why hi-- is nonetheless safe: we know nums[hi] == nums[mid] and mid < hi, so index mid holds an equal copy of whatever value sits at hi and mid stays in range. Even if hi was a position of the minimum, an equally small value survives inside [lo, hi−1]. We only ever needed the minimum value, not a specific index — and hi-- never destroys the last copy of it.

And why it is expensive: the loop's contract is normally “each iteration halves the range”. The tie branch shrinks the range by exactly one. Feed it [3, 3, 3, 3, 3, 3] and every single iteration takes the tie branch, so the search walks the array linearly: n − 1 iterations. Watch the ledger below the tape fill with dashed −1 pills.

Why compare against hi and not lo

In a rotated sorted array the right end is the reliable landmark. nums[mid] > nums[hi] means the descent (the rotation seam) sits strictly between them, so the minimum is at mid + 1 .. hi and mid itself is provably not it — lo = mid + 1. nums[mid] < nums[hi] means mid .. hi is a clean ascending run, so the minimum is at or left of mid — hi = mid, keeping mid as a candidate. Comparing against nums[lo] instead needs a separate “is this segment already sorted?” test, which is one more thing to get wrong.

The loop runs while (lo < hi), never ≤: there is no target and no failure case, so the moment the two pointers meet, that index is the answer. Return nums[lo].

O(log n) average · O(n) worst case (all elements equal) · O(1) space  ·  LeetCode 153's clean O(log n) is not free — it is bought by the distinctness precondition. Remove that precondition and nums[mid] == nums[hi] becomes uninformative, and the only safe response, hi--, discards one element instead of half.
