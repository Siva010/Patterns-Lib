Nothing here searches nums. The thing being searched is the answer itself — every candidate value for “largest allowed subarray sum”. The array only appears inside pieces(cap), a predicate that greedily fills subarrays up to cap and reports how many it needed. That predicate is monotone: a bigger cap never needs more pieces. So the feasible / infeasible frontier is one clean step, and a binary search walks straight to it.

Choosing lo and hi — the step people get wrong

lo = max(nums): one element can never be split, so no cap below the largest element is ever satisfiable. hi = sum(nums): one subarray holding everything is always legal (pieces = 1 ≤ k), so the answer can never exceed it.

  • Set hi too small and the answer sits outside the range — the search returns a value the predicate never actually accepted. Silently wrong.
  • Set hi too large and nothing breaks; you just pay a few extra iterations. When unsure, overshoot.

This is the G shape: minimise the maximum. Feasible means “this cap is generous enough”, so feasible pulls the ceiling down (hi = mid) and the answer is the smallest feasible candidate — lo at the end.

O(n · log(sum − max)) time · O(1) space  ·  pieces(cap) is non-increasing in cap; that single fact is the whole licence to binary search.
